# Правила стабильности аудио-движка и логирования на Desktop

При разработке аудио-функционала и контроллеров в данном проекте необходимо строго соблюдать следующие инженерные требования:

## 1. Прямой вывод логов в CLI-терминал
* Все ключевые события аудиосистемы (старт, пауза, остановка, изменение громкости, ошибки и исключения) обязаны дублироваться в `stdout.writeln()` / `stderr.writeln()` с точным таймштампом (`HH:mm:ss.SSS`).
* Это гарантирует, что при внезапном зависании или краше процесса в терминале `flutter run` останется видна последняя выполненная операция.

## 2. Асинхронность и неблокирующий аудио-движок
* На десктопных платформах (Windows / Linux) аудио-драйвер не должен выполнять синхронные блокирующие вызовы на основном потоке Dart (UI thread event looper).
* Используйте асинхронные неблокирующие драйверы (например, `audioplayers` через Windows Media Foundation) для всех операций воспроизведения и затухания.

## 3. Обязательная проверка существования локальных файлов
* Перед передачей локального пути в аудио-плеер ВСЕГДА выполняйте проверку:
  ```dart
  final file = File(filePath);
  if (!file.existsSync()) {
    LoggerService().warning('File does not exist: $filePath');
    return;
  }
  ```
* Запрещается передавать фиктивные или непроверенные пути в системный аудио-драйвер во избежание сбоев нативного процесса.

## 4. Сквозная реактивность в Provider (ChangeNotifier)
* Все дочерние контроллеры шин (`MusicBusController`, `AmbientBusController`, `SfxBusController`) должны либо проксировать свои уведомления в корневой сервис через `subController.addListener(notifyListeners)`, либо напрямую объявляться в `MultiProvider` в `main.dart`.
